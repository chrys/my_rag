# Specification: RAG Evaluation Dashboard - Generated Answers & History

This specification outlines the requirements, architectural design, and implementation plan for two new features in the RAG Evaluation workspace:
1. **RAG Generated Answers**: Persisting and displaying the actual answers generated by the RAG system during benchmark runs alongside the expected ground truth answers.
2. **Evaluation Run History**: Displaying a list of past evaluation runs in the sidebar. Choosing a past run displays its date, QA pairs, and historical scores in the main dashboard panel.

---

## 1. Objective & Scope

### Problem Statement
1. **Discarded Answers**: When evaluation runs, the synthesized answers are scored and then discarded. The dashboard shows the questions and ground truth answers, but does not display the RAG generated answers that produced those scores.
2. **No Run History Persistence in UI**: Although evaluation runs are saved in the database, the user cannot access past runs in the UI. Running a new evaluation overwrites the active content panel, and refreshing the page resets the workspace.

### Scope of Work
- **Database Extension**: Add `generated_answer` column to `EvaluationResultMetrics`.
- **Worker Logic Update**: Modify `execute_evaluation_run` to save the generated answer text.
- **Run History Sidebar Component**: Add a dynamic "Evaluation History" pane under the controls sidebar.
- **Historical Run Retrieval API**: Add a view that retrieves all past runs for a selected project and renders them as a list of links.
- **Past Run Loader**: Enable loading any past run's scorecard and metrics drill-down by clicking items in the history list.
- **Execution Date Display**: Update the main results header to display the run's completion date/time.
- **Editable QA Pairs**: Implement inline editing for QA pairs (Question and Ground Truth) in the drill-down diagnostics view, allowing edits to be saved back to the `EvaluationDataset` model.

## 4. Architectural & UI Design

### UI Layout: Sidebar History & Results Pane

```
+------------------------------------------+-------------------------------------------------+
| RAG Evaluation Workspace                 | Ragas Benchmark Results (June 11, 2026 17:10)   |
+------------------------------------------+-------------------------------------------------+
| Evaluation Config                        | [Total RAG Triad Score: 0.812 / 1.0]            |
| Target Project: [ Project A          ]   |                                                 |
| Method:         [ Ragas              ]   | [ Faith: 0.90 ] [ Rel: 0.82 ] [ Rec: 0.78 ] ... |
|                                          |                                                 |
| [ Run Benchmark Evaluation ]             | Trace Drill-Down Diagnostics                    |
|                                          | - Question: What is our refund policy?          |
|------------------------------------------|   Expected Ground Truth:                        |
| Past Evaluations                         |     Our policy allows 30-day refunds.           |
| - June 11, 2026, 17:05 (Score: 0.742)    |   RAG Generated Answer:                         |
| - June 10, 2026, 12:30 (Score: 0.812)    |     Customers can refund within 30 days.        |
| - June 08, 2026, 14:15 (Score: 0.650)    |   [Recall: 1.00] [Precision: 1.00] ...          |
+------------------------------------------+-------------------------------------------------+
```

### Dynamic Sidebar History Loader Flow
1. When the project selection changes:
   - Make an HTMX request to `/rag/evaluate/project/<project_id>/history/`.
   - Swap the response into `#evaluation-history-container` in the sidebar.
2. The endpoint returns `templates/evaluate/history_list.html`, rendering a list of runs ordered by `started_at` descending.
3. For each successful run, the overall score (`avg_total`) is shown.
4. Each run row in the list uses `hx-get="{% url 'evaluate:results' run.id %}" hx-target="#evaluation-content-pane"` to load that historical run into the workspace without page reloads.

### QA Pair Inline Editing Flow
1. In the drill-down panel under Trace Drill-Down Diagnostics, display an "Edit" button next to the question and expected ground truth fields.
2. Clicking "Edit" uses HTMX or client-side swapping to replace the read-only display with an inline form `templates/evaluate/qa_edit_form.html`.
3. The inline form contains `<textarea>` inputs for the question and the ground truth, along with "Save" and "Cancel" buttons.
4. Clicking "Save" triggers an HTMX `hx-post` (or `hx-put`) to `{% url 'evaluate:edit_dataset_item' dataset_item.id %}`, which validates the input, updates the database entry in `EvaluationDataset`, and returns the updated read-only HTML fragment.
5. Clicking "Cancel" reverts the form to the original read-only text view without making a network request.

## 5. Testing Strategy

- **Historical Runs View Test**: Test that `project_evaluation_history` returns the correct list of runs for the project and skips runs belonging to other projects.
- **Generated Answer Capture Test**: Verify that running the evaluator correctly records the LLM's response string in the database and renders it properly in the results template.
- **QA Pair Editing Test**: Verify that the dataset item editing view correctly validates input, saves the changes to the `EvaluationDataset` model instance, restricts access based on permissions, and returns the appropriate templates.
- **Regression Check**: Ensure existing tests pass successfully.

---

## 6. Guardrails & Boundaries

### Dos
- Ensure safe database reads (older runs might not have a `generated_answer`, handle as `"Not recorded"`).
- Order history descending by date to show the most recent run first.
- Handle empty/failed run history items gracefully.

### Ask Before
- Changing model structures for apps other than `evaluate`.

### Don'ts
- Do not run manual `git` commands from within the agent shell.
- Do not introduce blocking network requests on main HTTP cycles.
